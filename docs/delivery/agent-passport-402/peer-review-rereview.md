## Final Re-Review: Bounded Repair to Agent Passport Graph-Ordering Race

**Scope checked:** the diff delta since the prior review — serialized `append()` queue, visible graph-digest error state, overlapping-click Playwright proof, caller-digest-trust comment, and the per-action/aggregate cap scenario rework in `apps/gathergraph/src/passport/PassportDemo.tsx` and `tests/browser/proof-paths.spec.ts`.

### Findings (both low, non-blocking)

**1. Low — `apps/gathergraph/src/passport/PassportDemo.tsx`, `append()` (lines ~92–110) + all `void handlerFn()` call sites (`onClick={() => void alterTerms()}`, etc.)**
`append()` does `await queued` and lets that rejection propagate to its caller (`alterTerms`, `approve`, `runAuthorized`, `runDenial`). Every caller is invoked as `void handlerFn()` from an `onClick`, so if `queued` ever rejects, it becomes a silent unhandled promise rejection — no UI state changes, nothing announced to the user. In practice this is currently unreachable: `createGraphEvent` only throws on a negative/non-integer `sequence`, and `eventSequenceRef.current` is a monotonically-incrementing ref that can't produce one. No test exercises this path. Not a functional defect today, but if a future change makes `createGraphEvent` (or the crypto digest call inside it) fallible, failures would fail silently instead of surfacing via the existing `passport-outcome` `aria-live` region. Suggested fix: wrap the `void handlerFn()` call sites with a `.catch` that routes into the same visible error state used for `graphDigest` (`"INVALID GRAPH — REVIEW REQUIRED"` or an equivalent outcome), rather than relying on it being currently unreachable.

**2. Low — `apps/gathergraph/src/passport/PassportDemo.tsx`, authority-graph digest `<code aria-label="Authority graph digest">` (~line 470)**
The `graphDigest` rejection handler now visibly sets `"INVALID GRAPH — REVIEW REQUIRED"` (good — this is the fix for the prior "silent stall" finding), but the element it writes into has no `aria-live`/`role="status"`, so a screen-reader user not focused there wouldn't get a proactive announcement if this fallback state is ever reached. Since this state is defensive (the serialization queue is designed to make it unreachable) and the primary `passport-outcome` banner already covers the main success/denial flows with `aria-live="polite"`, this is minor. Suggested fix if hardened further: add `aria-live="polite"` to the digest `<code>` or move the invalid-graph message into the existing `passport-outcome` output.

### Verification of the specific concerns raised

- **Queue prevents out-of-order graph state:** Yes. `eventSequenceRef.current++` assigns sequence numbers synchronously in call order, and `eventQueueRef.current = queued.catch(() => undefined)` chains each `append()`'s async work (`createGraphEvent` → `setEvents`) strictly after the prior one settles, regardless of relative `crypto.subtle.digest` timing. This correctly closes the race the prior review flagged.
- **Errors surface accessibly:** Mostly yes — the `graphDigest` effect now has a `.catch` that sets a visible, non-"pending" string instead of silently freezing (verified by the test's `not.toContainText("pending")` assertion). The one gap (finding #2) is that this fallback text isn't wired to `aria-live`.
- **Overlap proof is meaningful and deterministic:** Yes. Dispatching two synchronous `HTMLElement.click()` calls inside one `evaluateAll` reliably fires both React `onClick` handlers synchronously up to their first `await`, genuinely overlapping two `append()` calls through the shared `eventQueueRef`. Because ordering is enforced by explicit promise chaining rather than by the relative speed of the underlying digest computation, the resulting order is deterministic. This is a legitimate fix for the diagnosed Playwright `Promise.all` actionability limitation (test-dispatch fault, not a product bug, as documented in `verification.md`).
